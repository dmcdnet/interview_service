❯ when splitting by counterparty, I need to specify the counterparty that is    
  being applied to the split.  This will have a name and id combination.        
  Furthermore for any split, I need to maintain WHAT that split is based upon,  
  i.e. a given counterparty split would be based upon that particular           
  counterparty.  Could you suggest changes that could be made which would model 
   this?                                                                        

● Here's how I'd model this in two steps:

  1. Introduce a Counterparty class and a SplitBasis marker interface

  // New: model/SplitBasis.java
  public interface SplitBasis {
      String getId();
      String getName();
  }

  // New: model/Counterparty.java
  public class Counterparty implements SplitBasis {
      private String id;
      private String name;
      // constructor, getters
  }

  SplitBasis is the general "what this split is based upon" contract. Right now
  only Counterparty implements it, but a future TradeSequence or LegDefinition
  could too without touching existing code.

  2. Add SplitBasis to Split, and carry Counterparty through 
  SplitRequestCounterparty

  // Split.java — add one field
  private SplitBasis basis;  // null for sequence splits, Counterparty for 
  counterparty splits

  // SplitRequestCounterparty.java — add counterparty
  public class SplitRequestCounterparty extends SplitRequest {
      private Counterparty counterparty;
      public SplitRequestCounterparty(String idToSplit, InterviewNodePath
  nodePath, Counterparty counterparty) {
          super(idToSplit, nodePath);
          this.counterparty = counterparty;
      }
  }

  InterviewProcessor.splitNode then passes requestCounterparty.getCounterparty()
   to InterviewUtility.counterpartySplitNode, which sets it as the basis on the
  new node's Split.

  Tradeoff to be aware of: using SplitBasis as an interface keeps things open,
  but if you need to serialise/deserialise Split with Jackson you'll need
  @JsonTypeInfo on SplitBasis to handle polymorphism. If that feels like
  overengineering for now, you could just put Counterparty counterparty directly
   on Split (nullable) and add more fields later when the need arises.

  Want me to implement this?

     Plan: Chained / Composable Splits

     Context

     Currently each InterviewNode carries a single Split object that encodes
     both what kind of split the node supports (from the YAML definition) and
     how the node was created (e.g. SN=1, isSplit=true). The path-cache key is
     derived from this single split, so a node can only ever have one qualifier:
      q1[SN=1] or q1[CP].

     The user needs to apply multiple split types in sequence to the same
     datapoint — e.g. first split a question by counterparty to get q1[CP], then
      split that copy by sequence to get q1[CP][SN=1]. The model must track the
     full chain of splits that created each node, and the path-addressing scheme
      must reflect the full chain.

     ---
     Core Design: splitHistory List on InterviewNode

     Add List<Split> splitHistory to InterviewNode. This list records every
     split that was applied, in order, to produce this particular node.

     ┌────────────────────────┬─────────────────────────────────┬──────────────┐
     │          Node          │          splitHistory           │   Path key   │
     ├────────────────────────┼─────────────────────────────────┼──────────────┤
     │ Original q1            │ []                              │ q1           │
     ├────────────────────────┼─────────────────────────────────┼──────────────┤
     │ Counterparty copy      │ [Split(CP, 1, cp)]              │ q1[CP]       │
     ├────────────────────────┼─────────────────────────────────┼──────────────┤
     │ Sequence copy of CP    │ [Split(CP, 1, cp), Split(SEQ,   │ q1[CP][SN=1] │
     │ copy                   │ 1)]                             │              │
     ├────────────────────────┼─────────────────────────────────┼──────────────┤
     │ Plain sequence copy    │ [Split(SEQ, 1)]                 │ q1[SN=1]     │
     └────────────────────────┴─────────────────────────────────┴──────────────┘

     The existing split field is kept unchanged — it continues to record the
     YAML-defined eligibility for the first split (used in
     InterviewDefinitionHandler). New eligibility rules are described below.

     private static int computeNextSequenceNumber(InterviewNode toBeSplit) {
         // The "base" history is the full history with any trailing SEQUENCE 
     entry removed.
         // All siblings that share this base history are in the same sequence 
     family.
         List<Split> base = baseHistory(toBeSplit.getSplitHistory());
         return ((InterviewContainer) toBeSplit.getParent()).getNodes().stream()
             .filter(n -> n.getId().equals(toBeSplit.getId()))
             .filter(n -> baseHistory(n.getSplitHistory()).equals(base))
             .map(n -> n.getSplitHistory())
             .filter(h -> !h.isEmpty() && h.get(h.size()-1).getSplitType() ==
     SplitType.SEQUENCE)
             .mapToInt(h -> h.get(h.size()-1).getSequenceNumber())
             .max().orElse(0) + 1;
     }

     // Strips a trailing SEQUENCE entry to find the "family root"
     private static List<Split> baseHistory(List<Split> history) {
         if (!history.isEmpty() && history.get(history.size()-1).getSplitType()
     == SplitType.SEQUENCE)
             return history.subList(0, history.size()-1);
         return history;
     }
